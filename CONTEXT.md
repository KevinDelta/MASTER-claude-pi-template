# CONTEXT.md — MASTER-claude-pi-template

> Domain glossary and architectural overview for this repo. Engineering skills read this before exploring the codebase. Fill in terms and concepts as they crystallise — use `/grill-with-docs` to drive this lazily from real decisions.

## What this repo is

A template system for building portable, domain-scoped knowledge worker agents on OpenClaw. The installer scaffolds an OpenClaw workspace with a routing table, domain persona, heartbeat tasks, memory, and project structure.

## Glossary

| Term | Definition |
|------|-----------|
| **OpenClaw** | The agent runtime and control plane. Manages agents, channels, identity, heartbeat, auth, and routing to isolated workspaces. |
| **Workspace** | `~/.openclaw/workspace/` — the single git-tracked directory where domain brain files and all project work live. |
| **SOUL.md** | Persona definition file. Describes the agent's identity, domain expertise, voice, and operating principles. Monolithic by design (one persona = one file), with a required internal outline — `## Mission`, `## Voice`, `## Principles`, `## Constraints` — so routing rows can address a single section (e.g. `SOUL.md#voice`) and load only the relevant slice. Multiple personas inside one domain go in separate SOUL files (see `domain/examples/SOUL.*.md`); splitting one persona across multiple files is explicitly out of bounds. |
| **SOUL section address** | A `file#section` reference in a routing-row `Read:` cell that targets one named section of a SOUL file rather than the whole file. Lets a drafting skill load `SOUL.md#voice` without dragging in mission/principles/constraints. Enforced by `lint-skills.mjs` against the required section list. |
| **AGENTS.md** | Routing table. Every turn, channel route, heartbeat, and project workflow resolves through a row here before work begins. |
| **HEARTBEAT.md** | Recurring task definitions. Owned by OpenClaw heartbeat. |
| **DOCK.md** | Export policy. Defines what the agent carries between sessions and what it can share externally. |
| **Domain** | A named scope of expertise installed via `./install.sh --domain <name>`. Appends routing + identity layers on top of OpenClaw's global config. |
| **Project** | A sub-scope within a domain, created via `--project-slug <name>`. Lives at `workspace/projects/<slug>/`. |
| **Intake** | The onboarding data contract (`master.json`) collected by the HTML wizard and consumed by `install.sh`. |
| **Routing row** | A single entry in `AGENTS.md` that maps an intent or channel to an agent and skill. |
| **Skill** | A reusable workflow or behavior modifier (e.g. `stop-slop.md`, `memory-write.md`). Describes *how* to do something — skills do not own output format. Shipped by the `domain-skills` plugin (core + per-domain tiers); discovered at runtime via `list_skills` and loaded by routing rows naming the file in `Load Skills`. |
| **`domain-skills` plugin** | OpenClaw plugin that owns the skill library. Ships universal skills under `core/` and domain-specific skills under `domains/<name>/`. Registers `list_skills`, `read_skill`, `install_skill`, and `remove_skill` MCP tools. Vendoring of third-party skills (e.g. Anthropic-marketplace `pdf`, `docx`) goes through `install_skill`, which wraps `openskills` with `--no-sync` to avoid mutating AGENTS.md. |
| **Skill tier** | A subdir inside the `domain-skills` plugin signalling scope. `core/` = universal (loaded for every install). `domains/<name>/` = domain-specific (loaded only when `--domain <name>` is selected). Resolution order is `core` → `domain` → `vendor` → `user` (last wins), so a user skill can shadow a vendored or plugin skill by reusing the filename. |
| **Vendor skill** | A skill installed into `~/.openclaw/workspace/skills/vendor/` via `install_skill` (which shells out to `openskills`). Distinct from plugin skills (shipped with the template) and user skills (hand-authored in the workspace). |
| **Template** | A reusable output shell (e.g. `executive-brief.md`, `weekly-status.md`). Describes the *shape* a deliverable takes. Skills fill templates; one template can be filled by many skills. Distinct from `skill` — skills are process, templates are shape. |
| **Workspace Pattern** | A reusable shape for a project or area: routing rows, context files, (optional) numbered stage subdirs, reference material, working-artifact locations, output templates, and edit-gate conventions. Distinct from `template` — templates are deliverable shells; workspace patterns are reusable work architecture. Also distinct from a `skill` (workflow). What ICM calls an "ICM workspace" maps to this term in MASTER. |
| **Inbox** | Human-curated staging area for raw upstream artifacts (call transcripts, meeting notes, clipped articles, voice memos). Lives at `base/inbox/` (project-scoped) and `domain/inbox/` (cross-project). Files land in `_inbox/`, get distilled via a routing row with human confirmation, then move to `_processed/`. **Distinct from memory** — inbox is the human's feed-in surface; memory is the agent's own observation store. Distillation never auto-writes to memory; the human decides what crosses that boundary. |
| **Distill** | The deliberate, human-triggered act of processing an inbox item — extracting insights and proposing where they belong (pillar/skill/decision/memory edit), then archiving the source. Always gated by user confirmation. |
| **Files-as-truth** | The memory ownership principle: workspace markdown files (`MEMORY.md`, `memory/*.md`) are the canonical record. The OC-native search index is a regenerable artifact, not a co-equal layer. |
| **Unpromoted observation** | A note written to the OC-native index during a session but not yet elevated to a `memory/*.md` file. Ephemeral by design — does not survive a domain move. The session-end routing row is the promotion checkpoint. |
| **Enforcement layers** | The three surfaces that implement DOCK.md policy: plugin schemas (tool-level), routing rows (think-time), and Gateway config (access boundary). Each layer changes independently; DOCK.md does not track their implementation details. |
| **Access category** | A named class of information the domain agent may expose (domain identity, memory recall, project status, skill discovery, structured writes, raw data export, commerce operations). DOCK.md declares categories and their default posture; plugin tools implement them. |
| **Commerce catalog** | A JSON file (`commerce-catalog.json`) in the workspace that lists approved services with Stripe price IDs, unit amounts, and slugs. The agent consults it before constructing any invoice line item or payment link. Seeded from `commerce-catalog.example.json` by `install.sh --enable-commerce`; price IDs must be replaced with real Stripe values before going live. |
| **Draft-before-send** | The two-turn approval pattern for all commerce mutations: turn 1 calls a draft tool and presents the result; turn 2 calls the send/execute tool only after the human explicitly confirms. Never advance in the same turn. |
| **Approval reference** | The human's literal confirmation message, carried as `approval_reference` on mutating Stripe calls. Paraphrasing is not allowed; ambiguous messages require a follow-up before proceeding. |
| **Reference (L3 / "factory")** | A file whose content is stable across runs of a skill — voice rules, client profiles, design conventions, glossaries, templates, skill bodies, sections of `SOUL.md`. The agent internalizes these as constraints. Borrowed from Interpretable Context Methodology: configure the factory, not the product. Tagged `[ref]` in routing-row `Read:` lists. The factory has tiers — see *Narrowest-scope rule*. Examples: `base/context/clients.md`, `SOUL.md#voice`, `templates/*`, `01_discovery/references/*`, most `skills/*`. |
| **Working artifact (L4 / "product")** | A file produced or consumed by a specific run of a skill — drafts, distilled notes, this-week's status, a single RFQ scoring sheet. The agent processes these as input, not as rules. Borrowed from ICM. Tagged `[work]` in routing-row `Read:` lists. Examples: `inbox/_inbox/*`, `areas/<area>/<artifact>_draft.md`, `areas/<area>/output/*`. |
| **Routing-row tag** | An optional suffix in a `Read:` cell — `[ref]` or `[work]` — declaring whether the file is reference (factory) or a working artifact (product). Enforced by `lint-skills.mjs`: producer-skills must not write to `[ref]` paths, distill-inbox must not treat `[work]` as durable rule. Pure documentation otherwise. || **Area** | A subdirectory under a project's `areas/` where a class of work happens (research, drafting, client-comms, triage). Every area has a `CONTEXT.md` at its root that orients the agent: purpose, workflow, standards, and — if it's a Staged Area — its stage list. Routing rows in project `AGENTS.md` target areas; per-area `CONTEXT.md` does not own its own routing rows. |
| **Staged Area** | An area whose work decomposes into numbered, ordered stages with explicit human edit gates between them (e.g. research → synthesis → delivery). Uses a `## Stage Sequence` section. Stage subdirs are zero-padded two-digit (`01_discovery/`, `02_synthesis/`). Mode declared implicitly: presence of numbered subdirs = Staged Area. (Was "pipeline area" in earlier drafts; see ADR 0010.) |
| **General Area** | An area whose work is one-shot — no numbered stages, artifacts land directly inside `areas/<area>/`. Uses a `## Workflow` section. Use when stage decomposition would be theater (a single draft, a one-shot triage). Mode declared implicitly: no numbered subdirs = General Area. (Was "flat area" in earlier drafts; see ADR 0010.) |
| **Stage** | One numbered step inside a Staged Area. Shape: `NN_name/{CONTEXT.md, output/}` minimum, with optional `references/` and `scripts/`. `CONTEXT.md` is the L2 contract with five canonical sections: `## Inputs` (L4 working artifacts) / `## Working References` (L3 factory) / `## Process` / `## Outputs` (names the canonical output file) / `## Verify`. `output/` is the L4 product and the edit-gate surface the human reviews before the next stage runs. The handoff is carried by `## Outputs` + the downstream stage's `## Inputs` — no `HANDOFF.md`, no status enum. `references/` is L3 stage-scoped factory; `scripts/` co-locates local non-AI automation. No `scratch/` (the agent's transient context is its session). See ADR 0010. |
| **Edit-gate surface** | A file or folder where the human reviews and optionally edits a stage's output before the next stage reads it. The `output/` folder of every Staged Area stage is one. The `inbox/_inbox/` distillation surface is another. The two-turn commerce approval pattern is a third. From ICM's "every output is an edit surface" principle (ADR 0009 principle 4). |
| **Narrowest-scope rule** | Reference material lives at the narrowest tier where it applies. Stage-scoped → `NN_stage/references/`. Project-scoped → `base/context/`. Domain-scoped → `domain/context/`. Global-scoped → `global/`. Prevents the L3 duplication antipattern (same voice rule copied into every Staged Area's delivery stage). Migration audit: for each file in current `context/`, ask "what scope?" and move to the narrowest fitting tier. See ADR 0009. |
| **State (in Staged Areas)** | Implicit, not a file. The current state of work in a Staged Area is "whichever `output/` folders contain files, and what they contain." No separate `STATE.md`, no per-stage status field. In General Areas, current state lives as a section inside `areas/<area>/CONTEXT.md`. |
| **Decision (operating)** | A choice made during the operation of a project or domain — pricing band, supplier shift, scope renegotiation, vendor selection. Distinct from a framework-architecture decision (those are ADRs in this repo's `docs/adr/`). Operating decisions live as append-log entries in `base/context/decisions.md` (project) or `domain/context/decisions.md` (domain) by default. |
| **Decision promotion** | The act of turning an append-log entry into a per-file record at `base/decisions/<slug>.md` or `domain/decisions/<slug>.md` when another load-bearing file (a stage `CONTEXT.md`, a skill, a routing row) explicitly cites the decision. The append-log entry is then replaced by a pointer to the promoted file. Rule: *if a decision is linked, it must be a discrete record; otherwise it's an append-log line*. Mirrors the inbox `_inbox/ → distill → _processed/` flow. |
| **Decision record shape** | The shape of a promoted decision file: `## Context / ## Options / ## Decision / ## Consequences / ## Owner`, with date in the filename (`YYYY-MM-<slug>.md`). Borrowed from sc-icm's `_template.md`. Lighter than an ADR (no "Status" lifecycle, no formal supersession chain — though a record may note `Superseded by: <slug>`). |
| **Execution mode (Staged Area)** | A declaration in the area `CONTEXT.md` header that sets how stages advance. `mode: human-gated` (default) — each stage requires explicit human invocation; the human's invocation IS the edit gate. `mode: autonomous` — the area walks its own stages end-to-end without human pauses; used for heartbeat-driven or trusted-routine pipelines (grounded in ICM §4.1/§4.4's orchestrator-walks-stages pattern). The mode lives in the area CONTEXT, not per-stage. See ADR 0010. |
| **Stage-targeted routing row** | A routing row whose `Area` cell points at a specific numbered stage (e.g. `/areas/research/01_discovery`) rather than at the area root. Used for human-gated Staged Areas — one row per invocable stage. Distinct from a stage-walking row that targets the area root and walks all stages (used only for `mode: autonomous` areas). |
| **Skill flavor scoping rule** | Producer-skills (skills that declare `Template:` front-matter and produce a shaped deliverable) are valid in **General Areas only**. Staged Areas use **modifier-skills only**; the stage `CONTEXT.md` owns output shape directly via its own `## Outputs` section (and an optional `Template:` reference). A producer-skill referenced from a staged-stage routing row is a lint error. Reasoning: stage CONTEXT is the per-stage contract; splitting shape across stage + producer-skill creates two surfaces of truth. See ADR 0010, extends ADR 0001. |
| **Operating principles (the five)** | The five named design principles MASTER inherits from Interpretable Context Methodology and uses as the discipline for structural decisions. (1) *One stage, one job* — each unit handles one step and writes its own output. (2) *Plain text as the interface* — markdown/JSON are the substrate; the rule that makes files-as-truth (ADR 0007) principled where MASTER has non-plain-text surfaces (`memory.db`, commerce state). (3) *Layered context loading* — each stage loads only the context it needs. (4) *Every output is an edit surface* — intermediate artifacts are reviewable and editable by humans before downstream steps consume them. (5) *Configure the factory, not the product* — reusable reference material is separate from per-run working artifacts. Live at the top of `xDOCS/BLUEPRINT.md` and cited in ADRs and reviews. See ADR 0009. |
| **L0–L4 layer model** | ICM's five-layer context hierarchy, adopted by role (ADR 0009). **L0** identity (`SOUL.md` + global `AGENTS.md` "Who You Are"); **L1** task routing (`AGENTS.md` routing table — MASTER's deliberate divergence from ICM's `CONTEXT.md`, because OpenClaw reads `AGENTS.md` natively and routing-table-first is the template's identity); **L2** the contract (area / stage `CONTEXT.md`); **L3** factory (`[ref]` files); **L4** product (`[work]` files). |

## What to avoid

- Don't call the routing table a "config file" — it's a **routing table**
- Don't call SOUL.md a "system prompt" — it's a **persona definition**
- Don't call the template a "framework" — it's a **template system**
- Don't call a reusable project or area structure a "template" when you mean routing + context + stages + gates — it's a **Workspace Pattern**
- Don't call DOCK.md an "enforcement spec" — it's a **policy declaration**; enforcement lives in the three layers
- Don't call `memory.db` / the OC-native index "the memory" — **workspace markdown is the memory**; the index is a regenerable search artifact
