# The template owns the routing contract and plugin trio; OpenClaw owns its bootstrap files and per-agent state

The template's architectural goal is to turn a generic OpenClaw agent into a domain-scoped knowledge worker via a routing-first contract plus a plugin trio (memory, skills, commerce). The template owns the files that constitute that contract — `AGENTS.md`, `MEMORY.md`, `context/`, `DOCK.md`, project scaffolds under `base/`, and the plugins themselves. It does not write to OpenClaw's bootstrap surfaces (`SOUL.md`, `HEARTBEAT.md`, `USER.md`, `IDENTITY.md`) and does not place content inside OpenClaw's per-agent state namespace (`~/.openclaw/agents/<name>/`). Where the contract needs to bind OpenClaw behavior on surfaces we do not own — most importantly the heartbeat — it does so through OpenClaw config strings, not file authorship. install.sh runs a single manual-mode install flow; the optional intake wizard accelerates *template-owned* file population only and never authors OpenClaw's bootstrap files.

## Considered Options

- **Keep appending domain content into OpenClaw's `SOUL.md` and `HEARTBEAT.md` (current behavior).** Rejected because shared authorship of a file OpenClaw also writes is a fragile contract — any change to OpenClaw's bootstrap format breaks the `sed`/`cat >>` append, and "who owns this file" stops being answerable. Conflates persona/recurring-tasks (OpenClaw's identity + scheduling surfaces) with domain routing (the template's spine).
- **Ship template-owned identity/tasks files alongside OpenClaw's, wired via a hypothetical OpenClaw "extras" config.** Considered and revised away. Identity needs to be ambient on every turn (not gated by a routing row), and reliable cross-version wiring for a separate identity file would require OpenClaw to expose a stable extras-bootstrap surface. Recreates the same coupling at a different layer.
- **Multi-domain native today: per-domain workspace, per-domain agent, multi-domain installer.** Rejected as premature. The plugin trio, skill tier dirs, and json5 reference already carry per-domain slugs (`domain-memory-<slug>`, `domains/<slug>/`, plugin paths) — those seams are forward-compatible. Building the multi-domain installer without a concrete second domain pulling at the design would produce abstractions we'd regret.
- **Place template workspace content under `~/.openclaw/agents/<DOMAIN>/`.** Rejected as a category error. `openclaw agents list` and `openclaw config get agents` confirm that `~/.openclaw/agents/<name>/agent/` is OpenClaw's *own* per-agent state directory; `~/.openclaw/workspace/` is the workspace path OpenClaw injects into the system prompt every turn. Multiple agents can share one workspace (OpenClaw verified two agents sharing `~/.openclaw/workspace` locally). Putting our domain brain files inside OpenClaw's per-agent state namespace would be invading OpenClaw's managed territory.
- **Wizard-required install (refuses to run without `--intake-json`).** Rejected as too rigid. Workers exploring the template, building a second domain for testing, or running without browser access cannot be blocked. The template has to work without the wizard.
- **Wizard-first with manual fallback (two install modes).** Rejected. Two modes mean two re-fill paths, two doc paths, and the wizard becomes the canonical mode — driving complexity nobody asked for. One install flow is the simpler shape.
- **Wizard authors OpenClaw's bootstrap files with `excludeBootstrapFiles` set.** Rejected once manual-mode-only was chosen. Once the template commits to never writing OpenClaw's surfaces, having the wizard author `SOUL.md`/`HEARTBEAT.md`/`USER.md` rebuilds the same coupling — just gated by intake JSON. `excludeBootstrapFiles` is documented in OpenClaw's config schema and remains available, but is never set by the template.
- **install.sh writes default heartbeat tasks directly into OpenClaw's `HEARTBEAT.md` as a one-time pragmatic exception.** Rejected. Re-opening file authorship for one file on convenience grounds unravels the ownership boundary across the board — the same argument would apply to persona scaffolds and worker-context conventions. The friction (one copy-paste at first install) is acceptable; the architecture either holds or it doesn't.

## Consequences

- **Template-owned files** (annotated scaffolds; teach in place; worker fills and deletes annotations): `global/AGENTS.md`, `domain/AGENTS.md`, `domain/MEMORY.md`, `domain/context/*.md`, `DOCK.md`, `domain/openclaw/openclaw.domain.json5`, `domain/openclaw/.env.example`, `base/*` (project layer), and the plugin trio under `domain/openclaw/plugins/`.
- **OpenClaw-owned files** (template ships nothing; `docs/agents/` teaches): `SOUL.md`, `HEARTBEAT.md`, `USER.md`, `IDENTITY.md`, and any future OpenClaw bootstrap file. New docs: `docs/agents/persona.md`, `docs/agents/heartbeat-tasks.md`, optionally `docs/agents/user-context.md`. `docs/agents/heartbeat-tasks.md` ships a "paste this whole block to get the default 5 tasks" section at the top — single copy-paste replaces the previously auto-emitted task list.
- **Opinion follows ownership** is the single rule that picks between the two patterns. No file is treated both ways. A lint check can prove no template content leaks into OpenClaw's bootstrap files.
- **Heartbeat binding without file ownership.** The routing-first contract binds heartbeat turns through `openclaw config set agents.defaults.heartbeat.prompt '…Resolve every recurring task through the AGENTS.md routing table before acting…'`. install.sh continues to write this config string. Workers add the task list to OpenClaw's `HEARTBEAT.md` themselves, guided by `docs/agents/heartbeat-tasks.md`.
- **install.sh changes**: drop the SOUL append block, the HEARTBEAT append block, and the USER.md write block. Single install flow (manual mode). `excludeBootstrapFiles` is not set. OpenClaw's default bootstrap creation runs untouched. install.sh's post-install message points at `docs/agents/` for OpenClaw-owned surfaces.
- **Wizard changes**: `apply-intake.mjs` keeps every template-owned rewrite (domain AGENTS.md sections, MEMORY.md seed, context files, DOCK overlay, per-project scaffolds). It deletes `appendSoulSection` and `appendHeartbeatSection`. The intake schema drops `setup.persona` (one-line persona description) and `setup.personaName` as a persona-identity field; install.sh's existing `--persona <name>` CLI flag continues to provide the name used for the shell alias.
- **Workspace path scheme**: stays at `~/.openclaw/workspace/` (matches install.sh's current behavior and OpenClaw's default). The repo-wide drift toward `~/.openclaw/agents/<DOMAIN>/…` for our content — present in `domain/openclaw/openclaw.domain.json5`, `xDOCS/BLUEPRINT.md`, `DOCK.md`, `domain/AGENTS.md` annotations, every plugin skill, and the `domain/examples/` SOUL files — is wrong and must be fixed back to `~/.openclaw/workspace/…`. Future multi-domain support uses `~/.openclaw/workspaces/<slug>/` (plural, our namespace) and the `openclaw agents add --workspace <dir>` flag, not OpenClaw's `agents/` namespace.
- **Single-domain today, multi-domain seams preserved.** Plugin install paths keep the slug suffix (`domain-{memory,skills,commerce}-<slug>`). Skill tier dirs keep `domains/<slug>/`. The flip to multi-domain becomes a `--workspace` change in install.sh plus per-domain `openclaw agents add`, not a path migration.
- **Re-fill behavior**: re-running install.sh with the same intake re-applies template-owned section rewrites (apply-intake uses `replaceSection`). OpenClaw's bootstrap files are never re-written by the template. Workers who want to update their persona or heartbeat tasks edit OpenClaw's files directly, using `docs/agents/` as reference.
- **Friction acknowledged**: after a fresh install, OpenClaw's `SOUL.md`, `HEARTBEAT.md`, and `USER.md` are empty (or carry OpenClaw's defaults). The agent is functionally bricked-on-first-run until the worker fills these. install.sh's final output names the three files and points at `docs/agents/`. This is the honest cost of the ownership boundary.
